# CLAUDE.md - AgentPulse

## Project Overview

AgentPulse is the command center for AI coding agents across all your machines. It monitors, orchestrates, and manages Claude Code and Codex CLI sessions from a single dashboard with chat-style prompt history, session notes, templates, managed launches, and remote access from any device.

## Tech Stack

- **Runtime:** Bun
- **Backend:** Hono (HTTP framework)
- **Frontend:** React 19 + Vite + TailwindCSS
- **State:** Zustand
- **Database:** SQLite (default, OSS quickstart) and PostgreSQL (production / multi-replica) — set `DATABASE_URL=postgres://...` to opt into Postgres. SQLite remains default when `DATABASE_URL` is unset or empty.
- **ORM:** Drizzle
- **Real-time:** WebSocket (native Bun); the dashboard also polls every 30 s whether or not the socket is up (3 s is the WS reconnect delay)
- **Telemetry:** Cloudflare Worker + D1 at `telemetry-agentpulse.xmojo.net` (default homelab endpoint; configurable via `TELEMETRY_ENDPOINT` env var in `src/server/services/telemetry.ts`)
- **MCP:** `@modelcontextprotocol/sdk` (stdio transport) + `zod` (tool input schemas) — lives in the `packages/agentpulse-mcp/` workspace member, publishes to npm as `@craze0/agentpulse-mcp` via the `mcp-v*` tag-triggered `.github/workflows/mcp-release.yml` (first published as 0.2.0 on 2026-10-12, with npm provenance; AGEN-52), see `docs/MCP.md` and `packages/agentpulse-mcp/README.md`
- **Linting:** Biome

## Commands

```bash
bun install              # Install dependencies
bun run dev              # Start dev server (API + Vite)
bun run dev:server       # Start API server only
bun run dev:web          # Start Vite frontend only
bun run dev:supervisor   # Start local supervisor only (watch mode)
bun run build            # Production build
bun run start            # Start production server
bun run check            # Run Biome linter
bun run check:fix        # Run Biome linter with auto-fix
bun run check:architecture  # Run all architecture guard scripts
bun run typecheck        # TypeScript type checking
bun run test             # Run test suite (bun test)
bun run test:watch       # Run tests in watch mode
bun run build:mcp        # Build the agentpulse-mcp package to dist/ (tsc, node-portable)
bun run check:mcp-tarball  # Pack agentpulse-mcp for real and audit the tarball (path allowlist, no sourcemaps/lifecycle-scripts/secrets)
agentpulse mcp serve     # Run the MCP server over stdio, from this checkout (for Claude Code / Codex CLI)
agentpulse mcp install   # Mint/reuse a scoped API key, print client config (see docs/MCP.md)
```

## Architecture

### Event Flow
```
Agent (Claude Code / Codex)
  → HTTP hook (async, never blocks agent)
  → localhost relay (if remote setup)
  → POST /api/v1/hooks
  → Event Processor (detect agent type, upsert session, store event)
  → DB + WebSocket broadcast
  → Dashboard UI (real-time updates)
```

### Database Schema

Schema is split across `src/server/db/schema/{core,ai,ask-projects}/` with per-table files and a column-factory pattern for dual-dialect differences. Per-dialect entry files (`schema/sqlite.ts`, `schema/postgres.ts`) export the canonical table set for each backend. The runtime barrel (`schema/index.ts`) reads `config.dialect` at module load and selects the appropriate per-dialect barrel; all production importers use it (the legacy `db/schema.ts` shim is deleted, guarded by `scripts/check-no-legacy-schema-import.ts`). Exports are currently cast to SQLite-typed variants for backwards type-compat; narrowing to dual-dialect generics is a follow-up.

- `sessions` - id, session_id, display_name, agent_type, status, cwd, model, is_working, is_pinned, git_branch, notes, semantic_status, current_task, plan_summary, total_tool_uses, metadata, timestamps, is_archived, last_agent_turn_completed_at, last_user_acknowledged_at. Note: `is_archived` is the canonical archive predicate; `status='archived'` is a legacy value retained for backwards-compat (see `src/shared/session-state.ts`). The two nullable acknowledgement timestamps (drizzle migrations sqlite `0007` / postgres `0008` + a legacy-init ALTER) back the operational WAITING-vs-IDLE distinction `getOperationalStatus` (`src/shared/session-state.ts`) computes, server-side (`mapSessionDto`'s `operationalStatus`) and client-side identically: `last_agent_turn_completed_at` is stamped on Stop, `last_user_acknowledged_at` on UserPromptSubmit, the synthetic `UserAcknowledge` hook, and `POST /sessions/:id/acknowledge` (server receive time for all, so they compare).
- `events` - id, session_id, event_type, tool_name, tool_input, tool_response, raw_payload, dedup_key, created_at. `dedup_key` is nullable server-derived durable identity for hook-delivered events (AGEN-16; null for events written by other paths — transcript, managed, AI). `idx_events_session_id_id` backs every session-scoped `ORDER BY id DESC` read; `uq_events_session_dedup_key` is a `UNIQUE(session_id, dedup_key)` index backing `ON CONFLICT DO NOTHING` inserts (NULL values never conflict with each other, so non-hook rows are unaffected).
- `events.occurred_at` (migration `0018`, both dialects) - nullable text: when the sender says a managed event happened. Display only and unauthenticated: the server keeps it only if it falls inside [receive - 25 h, receive + 5 min] (`OCCURRED_AT_PAST_MS`/`OCCURRED_AT_FUTURE_MS` in `managed-session-state.ts`), else stores null and logs one `occurred_at_rejected` line (no value) per supervisor per boot. It is never used for `created_at`, `last_activity_at`, acknowledgement stamps, ordering, retention, liveness, ownership, attribution or auth: `routes/occurred-at-readers.test.ts` scans the server tree and fails if a deciding file mentions it. `SessionEvent.occurredAt` is optional and omitted when null (also on the compact shapes); `check:dto-field-parity` covers `SessionEvent`.
- `managed_delivery_receipts` (migration `0018`) - `id`, `session_id` (inline `ON DELETE CASCADE` foreign key to `sessions.session_id`, on both dialects, so it is deliberately not in `rebuildSessionChildFks`), `receipt_key`, `created_at`; `UNIQUE(session_id, receipt_key)` and an index on `created_at`. `created_at` is written by the insert with `toDbTimestamp`, never a database default, so the prune's lexicographic compare matches event retention's. See the managed-delivery bullet under Key Conventions.
- `codex_approvals` (migration `0020`, both dialects; AGEN-87) - one row per managed Codex command or file-change approval request: `id` (the public id, a server UUID), `session_id` (inline `ON DELETE CASCADE` to `sessions.session_id`), `runtime_epoch` (a fresh UUID the supervisor mints per app-server spawn), `rpc_id` (`JSON.stringify` of Codex's request id, so `1` and `"1"` differ), `request_kind` (`command`|`file_change`), Codex's `thread_id`/`turn_id`/`item_id`/`provider_approval_id` (metadata, never on a response), `presentation` and `reason_text` (the redacted text a person is shown; **nulled when the row closes**, the hash stays), `presentation_hash` (sha256 of the canonical presentation JSON), `presentation_revision` (int32, minted by the supervisor's tracker), `approvable` and `not_approvable_reason`, `can_cancel`, `status` (`pending`|`answered`|`closed`), `closed_reason`, `host_outcome`, `decision`, `answered_by_user_id`/`answered_by_key_id`/`answered_at`, `first_delivered_at`, `last_issued_at`, `fenced_at`, and `created_at`/`expires_at`/`closed_at`/`updated_at`. `UNIQUE(session_id, runtime_epoch, rpc_id)` and indexes on `(session_id, status)`, `(session_id, created_at)` and `(status, expires_at)`. There is no supervisor column: the owning host is always read through `session-ownership.ts`. Every `closed_reason` write goes through `closeApproval` (a drift test holds it).
- `codex_approval_audit` (migration `0020`) - append-only, no foreign keys, outside event retention: `approval_id`, `session_id`, `host_name`, `actor_user_id`/`actor_key_id`/`actor_label`, `request_kind`, `revision`, `presentation_hash`, `decision`, `outcome` (`pending` until finalized), `created_at`, `completed_at`. Triggers on both dialects refuse a delete and refuse any update except `outcome` and `completed_at`, once, from `pending`. A `BEFORE DELETE` trigger on `codex_approvals` finalizes a still-pending audit row as `session_deleted`, or `session_deleted_after_issue` when `first_delivered_at` is set (that accept may have run). It stores the hash, not the words: deleting a session deletes its commands, and the record then shows who approved which version. **Accepted limits (review of phase 3):** running the database as a non-owner role and blocking `DROP TABLE` is deployment posture for every table, not this feature; a lost `first_delivered_at` is covered by `session_deleted_after_issue`; no code path uses `INSERT OR REPLACE` on these tables.
- `fork_tool_calls` (migration `0022`, both dialects; AGEN-123) - what each continued Claude session's tool call ran, for its owner: `id`, `session_id` (inline `ON DELETE CASCADE` to `sessions.session_id`), `turn_action_id`, `tool_use_id`, `tool` (one of the fork's tools or `mcp`, never an MCP server or tool name), `outcome` (`FORK_CALL_OUTCOMES`), `from_subagent`, `input_cipher`/`output_cipher` (AES-256-GCM under `AGENTPULSE_SECRETS_KEY`, the scheme provider credentials use), `input_truncated`, `output_truncated`, `redacted`, `created_at` (ISO text, milliseconds). `UNIQUE(session_id, tool_use_id)` and indexes on `created_at` and `(session_id, created_at)`. Only `services/fork-tool-detail.ts` reads or writes it (`fork-tool-calls-readers.guard.test.ts`). Without `AGENTPULSE_SECRETS_KEY` nothing is stored and the feature is off (see the owner-only tool detail bullet under Key Conventions).
- `supervisors.outbox_state` (migration `0019`) - nullable JSON text: the host's last heartbeat `outbox` report (below). Cleared by registration. Written in its own statement, only when the value changed, and a failed write is logged once (`heartbeat_outbox_state_failed`) and swallowed: the lease renewal and the heartbeat's answer never depend on it.
- `api_keys` - id, name, key_hash, key_prefix, is_active, scopes (JSON text, default `'["ingest"]'`), timestamps, `owner_user_id` (null = a service key, or undecided), `created_by_user_id`
- `settings` - key, value, updated_at. Three protected `instance.*` keys, written only by trusted callers (never through `PUT /settings`) and never returned by `GET /settings`: `instance.mode`, `instance.adminServiceKeyIds`, `instance.serviceKeyIds`
- Ownership columns (15 in all, migration sqlite `0006` / postgres `0007`, all nullable or defaulted; the legacy-init ALTER list carries the same): `sessions.owner_user_id`, `sessions.ingest_key_id` (the key that first reported the session; never emitted in a DTO), `api_keys.owner_user_id`/`created_by_user_id`, `supervisors.owner_user_id`, `supervisor_enrollment_tokens.created_by_user_id`, `control_actions.requested_by_user_id`, `launch_requests.requested_by_user_id`, `ai_action_requests.resolved_by_user_id`, and on `users`: `auth_source` (`local`|`sso`, default `local`), `provider`, `subject`, `subject_source` (`uid`|`username`), `display_name`, `must_change_password`. Indexes: `idx_sessions_owner_last_activity`, `idx_api_keys_owner`, unique `idx_users_provider_subject`. `supervisors.exclude_rules_state` (nullable text; only `"invalid"` is ever stored; sqlite `0008` / postgres `0009`) is the host's exclude flag.

### Launch privileges (approvalPolicy / sandboxMode)

- One mapping, `src/shared/launch-privileges.ts`, is used by the server (validation, preview, stored spec, launch DTO) and the supervisor (argv, Codex thread parameters). Unknown values and unsupported combinations are rejected, never defaulted; unset/`default` adds no flag.
- **What "enforced" covers**: the launch command line (Claude `--permission-mode`) and the managed Codex thread parameters, checked against what Codex reports. It does **not** cover the user's and project's own settings files, hooks or managed settings (`.claude/settings.json`, Codex `config.toml`), which can still widen permissions. Env that could redirect those (`HOME`, `CLAUDE_*`, `CODEX_*`, `AGENTPULSE_*`, `GIT_*`, `XDG_*`, `SSH_*`, `NODE_OPTIONS`, ...) is refused, and so is any name that is not `[A-Za-z_][A-Za-z0-9_]*` (a name containing `=` would be split by the child) (`src/shared/launch-env-policy.ts`). **This is a denylist over an open namespace, so it is defence in depth, not the boundary: the boundary is the trusted operator who may launch on a host at all.**
- The supervisor re-checks every launch and resume directory itself: no `..` segments, the deepest existing ancestor must resolve under a trusted root before prelaunch actions run, and the agent is spawned in the realpath that was checked, never the original string. A resume uses the launch row's model and cwd and this host's own bridge record, not anything the agent reported.
- The supervisor advertises `enforces_launch_privileges`; the server never routes, retries or claims a launch with a policy/sandbox to a supervisor without it, and fails a launch whose reported `providerLaunchMetadata.privileges.enforcedArgs` differs from the mapping.
- Prompts go after `--` on every Claude argv and may not start with `-`.
- **A managed Codex follow-up sends no overrides (AGEN-91).** `turn/start` carries `threadId` and `input` only, never `cwd`, `model`, `approvalPolicy` or `sandboxPolicy`: the thread's settings were set and checked at `thread/start` (`assertCodexThreadPrivileges`) and are sticky. `enqueuePromptInTx` leaves `env`, `approvalPolicy`, `sandboxMode` and `model` out of a Codex action's metadata, so they are never in the row; `cwd` stays only because the host's exclude gate judges it. A test holds the wire key set by equality, and the `followup` canary launches `untrusted`/`workspace-write` so a follow-up that lost the policy stops asking for approval and fails it.
- `launchSpec.providerConfig.cliArgs` is informational and built by the server from the template alone; the supervisor never executes a client-supplied value.

### AI control plane features
- Session intelligence classifier exposes `health` + reasonCode via
  `GET /api/v1/ai/sessions/:id/intelligence` and batch endpoint.
- Operator inbox at `/inbox` aggregates open HITL, stuck/risky sessions,
  and failed proposals as a discriminated-union read model.
- Project digest at `/digest` groups recent sessions by cwd with daily
  cache invalidated on refresh.
- Template distillation: `POST /ai/templates/distill` returns a draft
  template with provenance; user still reviews before saving.
- Launch recommendation: `POST /launches/recommendation` produces an
  advisory RecommendedLaunch; existing validator remains authoritative.
- Risk classes: `GET/PUT /ai/risk-classes` configure what counts as
  risky for `ask_on_risk` policy. Defaults cover destructive commands,
  credential references, and recent test failures.
- **Session watcher: two modes, one wake path.** Each `watcher_configs` row turns on **Notify** (a two-line status note for the owner when a turn ends) and/or **Continue** (a suggestion for the next prompt). New watchers follow `ai.watcherDefaults` (shipped Notify on, Continue off); existing rows migrated to Continue on, Notify off.
  - **Wake path.** Only turn boundaries wake the watcher (`boundaryOf` in `turn-identity.ts`: `Stop` and the managed turn ends are `turn_end`, `SessionEnd`/`ManagedSessionStopped` are `session_end`, prompts are `turn_start`). Hook ingest emits `watcher_wake` on the bus from its background task, only for sessions in `watched-sessions.ts`'s cached set (enabled with at least one mode; invalidated by every config write), so the 200 path and `ingest-latency.test.ts`'s statement budget are untouched; the supervisor path reaches the runner through `session_event`, narrowed to the same boundaries. The runner waits `BOUNDARY_DEBOUNCE_MS` (10 s) for a follow-up, re-checks `isAiActive()`, `isWatched()` and that no newer prompt exists, then `enqueueRun`. `enqueueRun` moves a *queued* run's trigger to the newer boundary (conditional update; 0 rows means it was claimed); a boundary that arrives during a run is held in `rewake` and woken for afterwards, with a process-local retry timer for `retryAfterMs`. The watcher's own `ai_*` events and `Ai*` event types never wake it, and neither hooks nor supervisors can write them (`normalizeHookEvent` and `appendManagedSessionEvents` refuse the names).
  - **Turn identity.** `computeTurnKey`: a Codex event's own valid `turn_id` (`t:<id>`; ignored for every other agent type), else the newest `prompt`-category event at or before the trigger (`p:<id>`), else `p:0`. `isTurnStale` is the one staleness rule (a different newest prompt, a later prompt, permission event or `PreToolUse`, the session working, a prompt control action after the trigger). Reports and proposals are unique per `(session, turn_key)` in the database.
  - **One run, in order:** config (no config, disabled or both modes off is `cancelled/not_watched`), **Notify**, **Continue**; a run that did neither is `cancelled/no_work`. Notify reads the evidence after the last *delivered* report (every `ai_*` row dropped), builds a 12,000-character ledger, makes one reasoning-off call, parses `{verdict, why, evidence}` strictly (no repair call; every cited id must be in the ledger), runs the text tripwire, suppresses the report if the turn moved on, then delivers to the inbox (`watcher_report`, cleared by acknowledging the session) and, within the rate rule, to Telegram as plain text starting with `AgentPulse summary; session content is untrusted.`. A transient failure is retried once (`claimReport` takes over a `failed` row with a transient code and attempts left; a `claimed` row is never taken over, and the startup sweep fails every one). Telegram: one routine report per session per 10 minutes, at most 3 escalations per session per hour, 30 messages an hour across all sessions with HITL requests counted, all counted from stored rows. Continue makes at most one proposal per turn, one model call a minute and six proposals an hour per session (counted from `watcher_proposals`). `maxContinuations` limits automatic sends only; a capped `auto` config still opens a request.
  - **The only send path is `dispatchPrompt`** (`proposal-resolution.ts`; a drift test pins every caller of `queuePromptAction(` and `enqueuePromptInTx(`). Its order is fixed: sanitise (a letter or digit first, no control characters, line breaks or force pushes) and the dispatch filter, before any database access; then one `withAdminLock` transaction with every statement on `tx` and no non-database await inside: the append-only audit intent row, uncached kill-switch reads, the turn staleness check, (auto only) the paused flag, the confirmed config, the caps counted from `control_actions` (6 an hour per session, 20 across sessions) and a live supervisor, the deliverability checks, then the conditional control-lock update and the `control_actions` insert. An expected refusal commits as an audit update; it never rolls back. `AiContinueSent` is emitted after commit by that function alone. `resolveProposal` claims the HITL row first (the loser gets `already_resolved`), checks the TTL (`HITL_TTL_MS`, 20 minutes) and the hash of the text the person saw, and releases the claim only for a refusal that enqueued nothing and only while the turn is current. A request with no trigger or hash is always stale. Callbacks carry only the request id and action; the prompt, hash and TTL always come from the server's rows (the reason there is no HMAC in `callback_data`).
  - **Auto** is for sessions AgentPulse launched, needs a person to confirm it from the dashboard (`auto_confirmed_at/by`; editing the system prompt, provider or limit lapses it, as does the confirmer losing access), and is paused by default (`ai.watcherAutoSendPaused`; both flags fail closed). It sends only the three fixed `CONTINUE_TEMPLATES` (`retry_failed_step`, `run_tests`, `summarize_status`; `proceed` is for a person only), never the model's words, and only after the deterministic human gate (`human-gate.ts`: the last agent message asks something, a permission request or notification is in the turn, or a risk class matches the last message or the pending tool call) and the text checks find nothing. Anything else becomes a request for a person. **Auto is Claude-only for now (AGEN-91):** on a session whose launch is `codex_cli` the decision falls through to `openRequest`, the same request `ask_always` opens, and `dispatchPrompt` refuses an `auto` send as `auto_send_blocked` / `codex_needs_person` (keyed on the launch, not the session row). The human gate reads hook-shaped evidence a managed Codex session doesn't produce, and auto ignores the launch's policy. Re-opening it is AGEN-112.
  - **A failed turn is never `finished`.** Notify turns a `finished` verdict into `needs_you` with the fixed note "The last turn didn't finish. Open the session to see what happened." when the trigger event is `HeadlessPromptFailed` or `HeadlessTaskFailed` (Claude's failed prompts too). The browser notification for a session that stops working says "stopped", not "finished" (`turn-stopped-notification.ts`), because the flag it watches flips for a failed turn too.
  - **Suggestions** are cleaned when written (`sanitizeOutboundPrompt`; the text a person sees is the text stored and hashed), stored once by `recordSuggestion`, and flagged `approvable` only when nothing had to be removed. A suggestion over 1,500 characters becomes a question. `proposalPrompt()` is what Approve, Copy and Telegram read. Deliverability (`prompt-deliverability.ts`) is one rule: AgentPulse launched the session, its host's lease is live and the control lock is free; otherwise Approve is Copy.
  - **Authorization.** The watcher config and decision routes are owner-or-admin (`OWNER_CHECKED_ROUTES`), do an `Origin` check, and validate strictly. Setting `auto`, resetting the counter and un-pausing or un-killing are human-only (a signed-in person, not an API key); those gates are inert under `DISABLE_AUTH`, which makes every caller a human. Config changes are audit-logged, the system prompt as a hash.
  - **Telegram.** One inbound gate (`authorizeTelegramCaller`) runs first for every update except `/start <code>`: a private chat, an active verified channel and the enrolled `from.id`. Enrollment codes are 96 bits, expire after 15 minutes and bind only a pending channel. A channel's owner is the user who created it; `"local"` belongs to nobody in team mode (its approvals are refused until an admin re-links it). Re-link reissues the code and keeps the channel id. Every outbound text is redacted and path-normalised (`telegram-text.ts`); `detail` is `minimal` by default and a group chat never gets `full`.
  - **Single replica.** The wake timers, the `rewake` map, the retry timers and the leaser's `inFlight` set live in the process; multi-replica operation is unsupported.
- Session summary (AGEN-69, Labs flag `sessionSummary`, default off): an
  on-demand, verified summary of one session, never automatic. The model
  answers against an evidence ledger of numbered events; the server checks
  every citation (the event exists, its kind and result), corrects a
  validation result the evidence contradicts, clamps an outcome the session's
  live state contradicts, and runs an instruction tripwire over the text. The
  summary is stored as a snapshot; `staleEvents` says how far the session has
  moved on. A summary call is priced at its worst case up front and settled at
  its real cost against the shared daily AI cap. Each model call has a time limit,
  `AGENTPULSE_SESSION_SUMMARY_TIMEOUT_SECONDS` (default 360, 30 to 1800, per
  call: the repair call gets it in full).
- Diagnostics: `GET /api/v1/ai/diagnostics` returns queue depth,
  flags, and OTel configuration. Structured `ai_metric` log events
  are emitted on every wake enqueue and run completion; opt-in
  OTel forwarding via `AGENTPULSE_OTEL_ENDPOINT`.

### AI gate rejection codes

AI routes return consistent rejection shapes. When writing code that calls AI endpoints:

- **404 / `{ error: "ai_disabled" }`** — AI is not compiled in (`AGENTPULSE_AI_ENABLED` is not set). `requireAiBuild`, and the first check of `requireAiActive`, in `src/server/routes/ai-gates.ts`.
- **409 / `{ error: "ai_disabled" }`** — AI is compiled in but switched off in runtime settings (Settings → AI watcher). Same code as the 404, different status: a client that branches on the code alone treats both as "not available", one that needs to tell "ask an admin to turn it on" from "this build has no AI" reads the status.
- **409 / `{ error: "ai_paused" }`** — AI is compiled in and runtime-enabled, but the kill switch is active. Watchers are paused; other AI features may still be available.

Both gates answer with a `message` as well; the session summary routes drop it and keep code and status. Read-only routes use `requireAiBuild` alone, so a stored result stays readable while AI is off or paused; routes that start AI work use `requireAiActive`. Do NOT use or document `503 / ai_kill_switch_active` — that code and message were never shipped. The actual contract is the codes above.

### Auth (two modes)
- `DISABLE_AUTH=true` - No auth, all endpoints open (default for local use)
- Auth enabled - API key for hooks, forwardauth SSO for dashboard (k8s deployment)
  - **Forwardauth trust secret**: `FORWARDAUTH_TRUST_SECRET` env var (required for SSO production deployments). AgentPulse works with any forwardauth-capable IdP — Authentik (default), Authelia, oauth2-proxy, Pomerium, Cloudflare Access. Traefik's `agentpulse-inject-verify` middleware injects the shared secret; AgentPulse verifies with `timingSafeEqual` + length guard. Configure header names via `FORWARDAUTH_HEADER_*` env vars (defaults are Authentik values). Legacy alias `AGENTPULSE_AUTHENTIK_TRUST_SECRET` accepted until v0.8.0. See `deploy/k8s/FORWARDAUTH.md` and `deploy/k8s/RUNBOOK-secrets-rotation.md`.
  - **Session bridge** (`src/server/auth/forwardauth-bridge.ts`, AGEN-5): on the first forwardauth-gated request, mints an `ap_session` cookie (8h default; `AGENTPULSE_SSO_SESSION_DURATION_MS`) so `/auth/me` and WS upgrades resolve the SSO identity through the existing cookie step. `auth_sessions` has four additive columns: `auth_source` (text, not-null, default `"local"`), `sso_subject` (nullable), `sso_username` (nullable), `provider` (nullable). The `auth_sessions.user_id` of an SSO session is the `users.id` of that person's own row (see Teams below); SSO callers are members unless their uid is in `AGENTPULSE_ADMIN_SSO_SUBJECTS`.
  - **`/auth/me` is un-forwardauth'd by design**: listed in the IngressRoute without the middleware chain. Moving it behind forwardauth would break local-auth fallback and double-set the cookie via the bridge. `Bearer ap_*` is authoritative when present — valid key → `api_key` identity; invalid/unknown key → 401 (the cookie is never consulted as fallback).
  - **Supervisor split**: dashboard-management routes at `/api/v1/admin/supervisors/*` (not in the IngressRoute exemption list; falls through to the forwardauth catch-all for live IdP revocation). Machine-agent routes remain at edge-public `/api/v1/supervisors/*` with supervisor-credential auth. The agent router is root-mounted (`app.ts`, AGEN-17) — ahead of the operator route bundle, at both `/api/v1` and `/app-api/v1` — not inside the bundle whose `requireAuth()`/`requireOperatorScope()` wildcards it would otherwise inherit. No operator API key is required or checked on agent routes; each handler carries its own supervisor-credential (or, for `register`, enrollment-token) check, and session ownership on top of that is enforced separately (`session-ownership.ts`, below). `src/server/app.public-surface.test.ts` is the regression guard.
  - **API key scopes**: every key carries an explicit capability set stored as a JSON array in `api_keys.scopes` (TEXT NOT NULL DEFAULT `'["ingest"]'`). Four recognized scopes: `ingest` (post hook events), `manage` (every operator route: supervisor enroll/rotate/revoke, API-key CRUD), `observe` (read-only, secret-free routes) and `respond` (the mobile companion; see the next bullet). The `*` wildcard is valid in DB records only (never accepted from a client request). `requireScope("manage")` remains only on the `supervisorsAdminRouter`; every other operator route, `/api-keys` included, is gated centrally by `requireOperatorScope()`. `requireApiKey` (hook path) enforces `ingest`. forwardauth / local sessions are never scope-checked — scoping applies only to `api_key` callers. Rejection: `403 { error: "insufficient_scope", required: "<scope>" }`. Default bootstrap key (`ensureDefaultApiKey`) gets `["ingest","manage"]` so fresh installs aren't locked out. Hook-setup flows (SetupPage, FirstRunWelcome) mint ingest-only keys. **Re-grant procedure**: mint a new key with the desired scopes via Settings (`POST /api/v1/api-keys` with `scopes` param), then revoke the old one — there is no scope-edit endpoint (mint-new + revoke-old is intentional). `channelsRouter` is gated by `requireOperatorScope()` too.
  - **Scope grants and `respond`** (`route-scope-policy.ts`): `SCOPE_GRANTS` is the one table of what each non-manage scope reaches: `{reads, writes, ws}` per scope, with a single matcher (`scopeGrantAllows`) that `requireOperatorScope()` uses. `OBSERVE_READ_PATHS` and `INGEST_WRITABLE_ROUTES` are views of it. `respond` reads everything `observe` reads and writes only `POST`/`DELETE /sessions/:sessionId/acknowledge` (owner-checked in the handler); it may open the WebSocket. It never implies `manage`, and it has **no approval grant**: the three Codex approval routes are in no `SCOPE_GRANTS` entry, a test asserts `SCOPE_GRANTS.respond` is unchanged by set equality, and no `respondApprovals` capability exists (a phone gets the push and sees WAITING, but can't answer). It lands with the phone client, in the same change as its guard, opt-in per device. Every literal manage check (`callerHasManageScope`, `scopesIncludeManage`, `service-keys.ts`, `PUT /settings`, `requireScope("manage")`) refuses it, and MCP ignores it (a respond-only key can't start the MCP server). **A grant lands only in the change that installs its guard**: add a route to `SCOPE_GRANTS.respond` and to `OWNER_CHECKED_ROUTES` (or its own guard) together; the drift tests require every grant to match a mounted route, no grant to be an admin route, and every respond read to be observe-readable or knowingly manage-only. `GET /api/v1/capabilities` (observe-readable) advertises features from `CAPABILITY_FEATURES` in `routes/capabilities.ts`; each entry names the route (or the WS upgrade path) that proves it, a test asserts it is mounted, and a `respond*` flag is advertised only when its grant exists.
  - **WebSocket authorization** (`ws/ws-auth.ts`, `ws/handler.ts`): the upgrade accepts a `manage` or `respond` key (or a human); `observe` and `ingest` get 403. A request with **no Origin** is accepted only for a valid `Authorization: Bearer ap_` key with auth on (a native client sends no Origin); a cookie or forwardauth identity with no Origin, and any socket with auth off, is refused, and a present Origin is always judged. A key without manage is a *restricted* socket and is forced into the `mobile` profile (`?profile=mobile` opts a manage socket in, shaped but not owner-filtered). A restricted socket cannot subscribe to `*` or to channels other than `sessions` and `session:<id>`; a `session:<id>` subscribe needs `canReadSession` (`authorization.ts`: solo always, team the owner, an admin, or any identified member for an unowned session; fails closed for a host credential, an unknown mode and a row with no owner field). It receives only an allow-list of message types: `session_created`/`session_updated`/`session_ended` for sessions it can read (a payload with no `ownerUserId` is denied), `new_event` on a `session:<id>` channel it holds, and `stats_updated` in solo only; any other type is denied. It never receives `new_event` on `sessions` or a `rawPayload`. **Mobile shaping:** `content` and `toolResponse` are cut to 2 KB with a sibling `contentTruncated`/`toolResponseTruncated: true`; an oversize `toolInput` stays an object holding a bounded preview (top-level entries that fit, string values cut to 256 bytes, large nested values omitted) with `toolInputTruncated: true`; the full text is a REST read away. Dashboard (manage/human) sockets keep the unfiltered team feed. **Limits:** inbound frames over 16 KB close the connection (`maxPayloadLength`), a subscribe may name at most 50 channels, a socket holds at most 200, `channels` must be an array of strings, control messages are token-bucketed per socket (burst 20, 2/s), and a key may hold at most 8 sockets at once (the 9th upgrade is refused with 429 until one closes). A subscribe the server refuses (too many channels, bad `channels`, bucket empty, per-socket limit) is answered with one `{type:"subscribe_rejected", reason}` frame (at most one a second per socket); clients ignore unknown message types. The sweep reads owners in queries of at most 500 session ids. **Ongoing authorization:** the 30 s sweep re-judges restricted sockets, and `requestWsRevalidation()` (`ws/revalidation.ts`) runs the same sweep at once after a session-owner change (`PATCH /sessions/:id/owner`, claim-unassigned, a launch assigning an owner), a role change (a launch assigning an owner and the creation-race first fill re-judge only when their guarded write changed a row), a mode switch, a key revoke or `PATCH /api-keys/:id`, and a user disable. A subscribe racing a sweep re-checks rather than trusting older state. **Close codes:** `4001` the credential is no longer valid (key revoked or deleted, user disabled, password change required: re-pair or sign in); `4003` the credential is valid but its authority changed (instance mode switched, key handed to another owner: reconnect); `1011` the server could not resolve authority (database error: reconnect). A respond key owned by an admin resolves to admin and reads every session in team mode. The feed filter is feed scoping, not isolation: team-mode REST reads are shared (see Residual limits).
  - **Teams (AGEN-64)**: the instance is `solo` (default) or `team`. Resolution order: `AGENTPULSE_MODE` (locks it; any other value refuses boot), the stored `instance.mode` setting, then solo. Nothing is cached: the mode is read from the database per request, so a switch is immediate on every replica. Boot also refuses team mode with `DISABLE_AUTH=true`, and env-locked team mode with no admin source. `PUT /instance/mode` is a human admin's, all-or-nothing under `withAdminLock`: switching to team needs a keep/assign/revoke decision for every active ownerless manage key (re-enumerated inside the lock, so a key minted mid-dialog can't slip past), and deactivates enrollment tokens with no creator.
  - **Identity**: `AuthUser` carries `userId` (users.id for a cookie or SSO caller, or an owned key's owner; null for a service key, `DISABLE_AUTH` or a host credential), `keyId` and `mustChangePassword`. SSO users get a `users` row on first sign-in, keyed by (provider, subject); the subject is the uid header when present (`subject_source: "uid"`), else the username (a recycled username would inherit the role and everything owned, so boot warns about admins identified that way). `forwardauthSubject()` in `user-identity.ts` is the one place the subject is derived. `AGENTPULSE_ADMIN_SSO_SUBJECTS` promotes only uid-sourced subjects.
  - **Access gate** (`requireAuth`): a disabled user, or a key owned by one, is refused; a user who must change their password (or a key they own) gets `403 password_change_required` on every route behind `requireAuth` except the change itself (the auth router — `/auth/me`, login, logout — is mounted outside it, and hook ingest uses `requireApiKey`, which isn't gated). `POST /auth/change-password` is exempt from forwardauth at the edge (a local account behind SSO can't otherwise reach it), requires a valid session in the handler, and allows 5 failed current-password attempts per account per 15 minutes (`password-change-limit.ts`, in memory).
  - **Roles and routes** (`route-scope-policy.ts`): `ALWAYS_ADMIN_ROUTES` need an admin in both modes (`humanOnly` ones refuse every API key); `TEAM_ADMIN_ROUTES` need an admin only in team mode; `OWNER_CHECKED_ROUTES` are decided in the handler through `authorization.ts`. Effective role: `DISABLE_AUTH` is admin; a host credential is `none`; a cookie or SSO user has their role; an owned key has its owner's *current* role (read with the key every request); an ownerless manage key is admin in solo and, in team, only if kept on `instance.adminServiceKeyIds`. `PUT /settings` is admin-only per key in team mode (the theme stays a member's). Mutating admin routes refuse a present, foreign `Origin` (`refuseBadOrigin`).
  - **Hook-path attribution** (`authorization.ts` `judgeForeignKeyWrite`, team mode only): an event for an owned session is dropped (still 200, counted as `foreignKeyDropped`) unless the posting key's owner owns the session, the key is the session's recorded `ingest_key_id`, the key's owner owns the session's host, or the session has a host and no recorded key and the key is an ownerless key on a service-key list (which then becomes its `ingest_key_id`). Session creation is limited per owner (or per ownerless key) by `AGENTPULSE_SESSION_CREATE_LIMIT` (default 120/min, team only, counted in memory per replica); API-key minting is limited to 10/min per caller.
  - **Residual limits, by design (take over, AGEN-115)**: `host_owner_mismatch` (a host owned by someone other than the session's owner is refused for everyone, an admin included: change the owner first) and `session_key_mismatch` (a member takes over only a session whose recorded ingest key belongs to someone who owns the target host) are the guards; **on one shared OS account a member can forge a row with their own key for a thread that belongs to someone else on that account, and take it over (D5, accepted: attribution is by key possession)**; an unowned session taken over by an admin gets an owner only when it works (the host's owner, else the admin), and the dialog says so.
  - **Residual limits, by design**: team mode shares every read (observe-scoped keys included); a host's owner can read and write sessions launched on that host; any member can launch on any host; ownership is attribution by key possession, not authentication of a person.

### Relay (for remote server users)
Agents post hooks to a relay on the same machine (`scripts/relay.ts`, listening on `127.0.0.1`), which queues them on disk and forwards them, with the API key, to the remote server; it also applies the user's exclude rules before anything is stored or sent. LaunchAgent auto-starts it on macOS login. Whether Claude Code would post directly to a non-loopback URL was never measured (see `src/shared/hook-runtime-observations.md`), so don't state either way.

- `GET /setup-relay.sh` - Self-contained relay + hook setup script

**Hook ingestion (API key when auth enabled):**
- `POST /api/v1/hooks` - Receive hook events from Claude Code / Codex (always returns 200; rate-limited drops are silent, counter exposed in /health). Request bodies over 16 MiB are dropped before parsing rather than stored in full — still 200, counted in `oversizeDropped`; when enough identity survives the truncated prefix, a placeholder row is stored so the delivery isn't silently invisible. Optional `X-AgentPulse-Delivery-Id` (a caller-stamped stable id for a retriable delivery — relays, the Codex observer) and `X-AgentPulse-Origin: codex-observer` (identifies the supervisor's own Codex rollout-file observer) headers drive durable hook-delivery dedup (AGEN-16); both fall back to best-effort behavior when absent. Any top-level payload key starting with `agentpulse_` (case-insensitive) is stripped before processing — that prefix is server-reserved. Also accepts the synthetic `UserAcknowledge` event (`{ hook_event_name: "UserAcknowledge", session_id, transcript_path?, cwd?, source, acknowledged_at }`, `AgentPulseSyntheticEvent` in `src/shared/types.ts` — not a CLI hook, so deliberately outside the parity-guarded `ClaudeCodeEvent`/`CodexEvent` unions): it stamps `lastUserAcknowledgedAt`, stores one `user_ack` event, never sets `isWorking`, never creates or reanimates a session (an ack for an unknown session is dropped — `processHookEvent` returns `session: null` and the route broadcasts nothing), never clears a permission wait, and is dropped silently (still 200, nothing stored) unless the session has no owner or the posting key's owner is the session's owner: an owned session is not acknowledged by a key with no owner (a service key, or no caller context) or by someone else's key, and the hook path has no admin override (`canAcknowledgeOwnedSession`, which asks the same `mayClearAttention` rule as the REST routes).
- `POST /api/v1/hooks/status` - Receive semantic status updates (same 16 MiB body cap and always-200 contract as `/hooks`; oversize bodies are dropped and counted, with no placeholder row)
- **`X-AgentPulse-Skip` on `/hooks` and `/hooks/status`** (AGEN-63): `skipHeaderDrop()` is mounted with `ingest.use(path, …)` ahead of each route's own `requireApiKey()` + `hookRateLimit()`. A header value in the skip allowlist (`1`, `true`, `yes`, `on`, case-insensitive, trimmed; over 64 chars is "not set") is authenticated with `requireApiKey()` itself (so a bad key still gets its 401/403), then answered `200 {ok:true}` without reading the body, spending a rate-limit token, or touching the database; counted as `skipHeaderDropped` on `/health`. Any other request passes through untouched. A skip request skips the route's later checks on purpose: it changes nothing, so there is nothing for them to protect.

Pagination (`limit`/`offset`) and `total` stay correct under this filter — candidates are classified before paging, not a second SQL implementation of the precedence rule.

A value outside the grammar (a control or format character, over 256 characters) is `400 { error: "invalid_host", value }`. List rows and the session a card action returns carry `machine` (the effective machine, or null; absent on the detail response and from an older server). `GET /sessions/stats?group_by=host` returns one row per machine (`HostStatsGroup`: `host`, `total`, `active`, `idle`, `completed`, `tabCounts`, `working`, `waiting`, `error`), by name, the sessions with no machine reported (`host: null`) last, counted like `group_by=owner` (a fixed number of statements however many machines; past the candidate cap each machine keeps its own attention rows) and composes with `owner=`, `excludeScratch` and `host=` (which narrows it to that machine's one group). **It is bounded**: an ingest key can mint any number of machine names and every viewer's 30 s poll asks for this, so the listing is the sessions with no machine reported (always), the machines that have sessions and that a registered, non-revoked supervisor names (always, up to `MAX_REGISTERED_MACHINE_GROUPS`, 200; registering a supervisor takes a manage-level credential, so an ingest key can't inflate this part or push a supervisor-registered machine out of it (a machine only a relay reports has no such protection: invented busy names can still push it into the rolled-up remainder); the listing is built from sessions, so a registered machine with none isn't listed: the filter selects sessions and there would be nothing to show), and the busiest `MAX_MACHINE_GROUPS` (50) of the rest (ties by name); everything else is one explicit figure, `otherMachines` and `otherTotal`, with `groupsTruncated: true`. It is still one statement (nested subqueries with window functions). (`truncated` still means the working/idle columns may under-count.) The truncated listing is approximate for machines no supervisor registered: a flood of invented names can crowd a real quiet reporting-only machine out of the busiest 50, which is why a chosen machine outside the list is still shown and selectable in the dashboard, without a count. A machine's count includes sessions that only claim that name (the name is self-reported).
- `GET /api/v1/sessions/stats` - Dashboard KPI stats. Also carries `operational: { waiting, working, idle, error }` (AGEN) — the same four counts the status cards show, correct beyond whatever page size a client fetched. `?owner=` scopes every count (`me`, a user id, `unassigned`, `service`, `all`), and the response echoes the scope it applied as `ownerScope: {kind, userId?}`, plus `total` (every session in that scope) and, with `excludeScratch=true`, `scratchHidden` (how many scratch-workspace sessions that left out of every count). `group_by=owner` returns per-owner rows instead. `GET /sessions` takes the same `owner` and echoes `ownerScope`; `limit` is an integer 1 to 5000 and `offset` 0 to 1,000,000 (anything else is a 400), and `fields=` can't be combined with `operational=`.

- `POST /api/v1/supervisors/:id/heartbeat` — optional body `{ "excludeRulesState": "invalid" }`, sent only while the host's exclude file or the gate's saved state is invalid. The server stores only `invalid` (`none`/`ok` clear the flag, as does a heartbeat with no or an empty body; an unrecognised, oversized or unreadable body leaves it as it was). A heartbeat is never rejected for this field, since a rejected heartbeat makes the supervisor exit. `list_hosts`/`GET /admin/supervisors` return it as `excludeRulesState`. The body may also carry `outbox` (AGEN-83): `{ pending, oldestPendingAt, lastFlushAt, lastFlushDelivered, lastFlushLost }`, sent only while the host's offline outbox holds something or within 24 h of a flush. A body, when there is one, always carries `excludeRulesState` (`"invalid"`, or else the constant `"none"`, which old and new servers both read as clear), so an older flag is cleared by a newer body. The server clamps counts to [0, 10,000,000] and nulls a time outside [now - 30 days, now + 5 minutes]; a body with no `outbox` (an older supervisor, a host with nothing to say) or `outbox: null` clears the stored value, and an unreadable body or a malformed `outbox` leaves it. It is returned as `SupervisorRecord.outbox` (absent when none) and the host's capabilities advertise the feature `offline_outbox`. **The stored value is never aged**: it is the last one the host reported, so `list_hosts` and the Hosts page must gate it on the live lease (the web does; MCP callers should). - `POST /api/v1/supervisors/:id/managed-session-state` and `POST /api/v1/supervisors/:id/managed-sessions/:sessionId/events` (AGEN-83) carry a 2 MiB body limit (`413 payload_too_large`); a malformed body, or an event with a wrongly typed or oversized field, is `400 invalid_body` (a new supervisor drops that entry as lost). Optional headers: `X-AgentPulse-Delivery-Id` (events only, see the managed-delivery bullet) and `X-AgentPulse-Replay: 1` (`REPLAY_HEADER` in `src/shared/hook-headers.ts`), which a supervisor sets on a report it sends from its offline outbox, and from a bridge spool file that waited longer than `LATE_ARRIVAL_MS` (60 s, `src/shared/late-arrival.ts`). Lateness is decided only by that authenticated sender's own queueing, never by an event's own time. Replays are capped per process: at most 4 in flight (`MAX_CONCURRENT_REPLAYS`) and 2 from one supervisor (`MAX_REPLAYS_PER_SUPERVISOR`), the slot taken after the credential check and after the body has been read and validated; the rest get `503 { error: "busy" }` with `Retry-After: 2`, which a supervisor treats as back-pressure. Live reports are never counted or refused. A replay's events are stored and broadcast on the WebSocket, but `session_event` carries `late: true` (and `session_updated` gets a second `{ late: true }` argument on the bus), and the listeners that mean "something just happened" skip it: `AiWatcherRunner.onSessionEvent` (no `stampUserPrompt`, no wake), the inline embedder (`embedLiveSessionEvent`; the paced backfill picks the event up) and the Live Activity publisher (no trace tick). A late `session_updated` is coalesced per session by the publisher into one refresh with the latest state after 2 s of quiet and at most 10 s after the first, so a replayed terminal state still ends the activity without a burst.
- `WS /api/v1/ws` - Real-time event stream. Each connection carries the opener's user id and key id (from the upgrade guard); a heartbeat-interval sweep (30 s) closes sockets of disabled users and users who must change their password, and disabling a user or resetting a password closes theirs at once. Broadcasts are **not** filtered by owner: every signed-in browser gets every update, by design. The upgrade checks `Origin`: the configured allowlist, or the request's own origin, and with `DISABLE_AUTH=true` only when the Host is a loopback address or an allowlisted name.

## Key Conventions

- Biome for formatting (tabs, double quotes, semicolons)
- Dark theme is default
- Hook ingestion must be fast (< 50ms response, always return 200)
- SQLite datetime format: "YYYY-MM-DD HH:MM:SS" (no T/Z) -- use `parseDate()` (import from `src/web/lib/utils.ts`) in frontend
- Session names generated from adjective-noun pairs (name-generator.ts)
- **Hook-delivery dedup (AGEN-16)**: hook-delivered events (source `POST /api/v1/hooks`) are deduplicated by durable identity, stored in `events.dedup_key`, not by comparing content. Three key namespaces, each the first 32 hex chars of a sha256 over length-prefixed fields: `t:` keys a tool call or permission event by its own `tool_use_id`; `d:` keys everything else in a delivery by a hash of the whole delivery body (so a retried non-`t:`-eligible event dedupes only when the caller also stamps `X-AgentPulse-Delivery-Id`); `o:` is the oversize-stub placeholder's own namespace, keyed on `tool_use_id` or the delivery id, so a stub can never collide with (or suppress) a real `t:`/`d:` row. A `UNIQUE(session_id, dedup_key)` index backs `ON CONFLICT DO NOTHING` at insert time. Events from other write paths (transcript reconciliation, managed-session state, AI proposals) keep the older content-window dedup and always store `dedup_key: null`.
- **Managed-delivery receipts (AGEN-83)**: a supervisor's managed events batch is deduplicated by a receipt, not by `dedup_key`; the rows still store `dedup_key: null`. With a well-formed `X-AgentPulse-Delivery-Id` (8 to 64 of `A-Za-z0-9-`), `insertManagedEvents` runs one transaction, every statement on `tx` (`loadRecentRows` included): it inserts the receipt first, `receipt_key` being the first 32 hex of a sha256 over the length-prefixed supervisor id, delivery id and a digest of the raw body text (`computeManagedReceiptKey`, so a reused id with different content is a new delivery); a conflict means a replay, nothing is stored and `deliveryRetry` is counted; otherwise the rows go through the same content-window plan and insert as before. The receipt is written even when the window then drops every row (that is what lets a later replay of it be recognised), and a failed insert rolls it back. An insert is chunked at 500 rows a statement inside that transaction, with no cap on the batch itself. Without the header, or with a malformed one, only the content window applies, as before. The supervisor gives every events batch a delivery id on its first live attempt, so **every non-empty live managed batch now writes one receipt row**, pruned after 72 h. State reports carry no delivery id: the upsert is an idempotent patch.
- **Session-scoped event reads are ordered by `id DESC`**, not `created_at DESC` — row id is monotonic and unambiguous for events created in the same instant; `created_at` is not. `idx_events_session_id_id` backs this.
- **SQLite FTS rowid convention**: every `search_events_fts` write and delete uses `rowid = events.id` (not the `event_id` column, which exists only because search reads it directly) — an FTS delete keyed by `rowid` is a constrained lookup instead of a full-table scan. The DDL lives in exactly one module, `src/server/db/fts-ddl.ts`, imported by both `db/client.ts`'s boot bootstrap and the SQLite search backend.
- **Codex observer (AGEN-16)**: the local supervisor's Codex-observer fallback (`src/supervisor/services/codex-observer.ts`) tails `~/.codex/sessions` rollout files and posts hook-shaped events for hosts where native Codex hooks aren't covering a session. It stamps `X-AgentPulse-Delivery-Id`/`X-AgentPulse-Origin: codex-observer` on every post, posts one turn-completion row per Codex turn (not per assistant-message chunk), and skips a session entirely once a per-session marker file (`~/.agentpulse/codex-native/<session_id>`) shows native Codex hooks already cover it — a missing marker means it posts (fail-open). `AGENTPULSE_CODEX_OBSERVER=off` disables it outright. Each scan replays at most 1 MiB and 500 lines per file (the offset advances by exactly the bytes of the complete lines consumed; the rest waits for the next scan) and a scan never overlaps the previous one. Candidates are today's date directory plus `AGENTPULSE_CODEX_BACKFILL_DAYS`, and any file written within `AGENTPULSE_CODEX_RESUME_WINDOW_HOURS` (default 24, `0` = off) anywhere under the sessions tree, found through the cached listing in `codex-rollout-index.ts`; such a resumed file first seen outside the recent date directories (named for the UTC or the local date) is judged by the exclude rules first, then followed from its first line timestamped in the last 15 minutes, found in a 256 KiB tail (its end if none), and one real file reached through symlinks is followed once.
- **Effective machine and the machine filter (HF1-HF3)**: a session's machine is the supervisor's host (`managed_sessions.host_name`, non-blank) for a supervisor-launched session, else `sessions.reported_host`, else none (blank is none); one definition in `src/server/services/effective-machine.ts`, written three ways for cost (a per-row lookup for a page, uncorrelated membership tests for the filter, a join for the grouping) with a test holding them equal on awkward data. The query grammar, the row rule (`machineMatchesHost`) and the echo check (`hostEchoMatchesRequest`) live once in `src/shared/machine-scope.ts`; the MCP package carries a vendored copy held equal by `src/shared/machine-scope-mcp-parity.test.ts`. Filtering and grouping are **server-side**, like the owner scope, so tabs, status cards, Load more, search and counts all describe one set. **It is a view, never an access decision**: `reported_host` is self-declared and unauthenticated, so no auth, ownership, routing or attribution code may read it (`ingest-reported-host.test.ts` scans for that; its allowlist holds only the display/filter sites). Live updates: the WS broadcaster (`initWsBroadcaster`'s `annotate`, wired in `index.ts` with `stampMachine`) stamps `machine` on every pushed session, looking up concurrently but sending in emit order (session events included, so a creation still precedes its first event); a push that can't be stamped is sent as it was and the dashboard treats a row with no `machine` field as "can't tell" (kept if shown, never added on a guess, the same fail-open as an ownerless row), while `machine: null` means no machine. The dashboard keeps the choice in `dashboard-scope-store` (`host`, persisted per person under `agentpulse.dashboard.host.<user>` by `useHostScope`), carries it in `DashboardScope.host` so every request is built with it (the list, tab and status lists, Load more, stats, the per-owner headers, Mark all as seen, and the team line's "everyone" half), and offers it from `group_by=host` (`useMachineStats`, always about every machine). With one machine (or none reported) across everyone the control isn't drawn (the count is the install's, not the owner on screen's, and the last known value holds while a new answer loads and across visits); it stays while a machine is chosen or Group by Machine is on. The sessions with no machine are called "No machine reported" everywhere. A supervisor's host name is written by the supervisor, so it is cleaned like a reported name (`services/machine-name.ts`: at registration, when a managed session copies it, and once at every boot for rows stored by an older server) so the grammar, the SQL and the dashboard's trimming can't disagree about a name the grouping lists; a name that can't be expressed as a filter is refused in the dashboard, never turned into "all machines". The socket stamp is bounded: per-session ordering, a 250 ms lookup timeout (the row then goes out unstamped, which the dashboard reads as "can't tell") and at most 200 lookups in flight (a timed-out lookup's query isn't cancelled, only bounded by that count). The cleanup at boot is cosmetic and can't stop it: a failure is logged as one `machine_names_cleanup_failed` line and boot continues; a stored supervisor whose name has nothing printable in it is renamed, by id, to the name registration falls back to ("unnamed host"), and its managed sessions' copies follow. The card's host label (`lib/session-host.ts`) reads the same `machine` the filter selects on.
- **A state is said once in the UI.** The operational badge (`getOperationalStatus`, the one classifier; it already counts the raw `isWorking` flag and the agent-reported `semanticStatus` waiting evidence) is the authoritative state and always shows. No second chip may spell a state word beside it (the session header used to add a raw-`isWorking` "working" chip: `components/session-detail/header-status.test.ts` guards that). `semanticStatus` (researching, implementing, testing, debugging, reviewing, documenting, planning, waiting) is not rendered by the web at all today; if a chip for it is ever added, it should show only values outside the operational vocabulary (working, waiting, idle, error) and never repeat or contradict the badge.
- **Reported host (`sessions.reported_host`)**: the machine name a relay or the Codex observer sends in `X-AgentPulse-Host` (percent-encoded; `HOST_HEADER` in `src/shared/hook-headers.ts`, parsed and cleaned by `src/shared/reported-host.ts`: trimmed, control/format characters stripped, 128-character cap, empty rejected). **Display only and unauthenticated** — the sender picks it, so no ownership, access, routing or other decision may read it (`ingest-reported-host.test.ts` scans the auth and attribution modules for it). A nullable column rather than `metadata`: typed, indexable, and kept apart from operator-authored content. It is folded into the session UPDATE the processor already issues, and only when it differs from the row already read, so a hook adds zero statements. Direct-mode hooks (Claude posting straight to the server, the Codex/Copilot shell commands) send nothing and show no host. A managed session's host (`managed_sessions.host_name`) outranks it in the UI (`src/web/lib/session-host.ts`). `scripts/relay.ts` carries its own copy of the header name (it cannot import `src/shared/`); a test pins the two equal.
- DB migrations: SQLite fresh installs and all Postgres installs use Drizzle migrate (baselines in `drizzle/sqlite/` and `drizzle/postgres/`; the two dialects' migration numbers only stay in lockstep when a schema change applies to both — Postgres-only migrations like `0006` (AGEN-27) leave SQLite at its last shared number, so the acknowledgement-timestamp columns are sqlite `0007_session_ack_timestamps` / postgres `0008_session_ack_timestamps`). Existing SQLite installs use the legacy `initializeDatabase()` path unless `AGENTPULSE_LEGACY_INIT=false`. Schema changes must generate two migrations in lockstep: `bun run db:generate:sqlite` and `bun run db:generate:postgres` (a Postgres-only change still runs both — `db:generate:sqlite` simply produces no new file when nothing in `schema.sqlite.ts` changed). The numbers have since converged: sqlite `0010_event_embeddings_scan_index` is SQLite-only (the embeddings table has no Postgres counterpart), and it brought SQLite level with Postgres's `0010_session_reported_host`, and both folders now end at `0020` (`0018_managed_delivery`, `0019_supervisor_outbox_state`, `0020_codex_approvals`), so list both folders for the next number. Don't read the earlier "SQLite is one behind" offset into a newer migration without listing both folders. An index on the SQLite-only embeddings table is created both by that Drizzle migration and, for installs on the legacy init path, by the legacy init's additive list in `db/client.ts`, which creates the embeddings table and this index whatever the vector flag says (only the delete trigger and `idx_event_embeddings_model` stay behind `config.vectorSearchEnabled`); the two must stay in step. A migration that adds an index should use `IF NOT EXISTS` in both dialects so a large-table operator can pre-create it out-of-band (`CONCURRENTLY` on Postgres) without the in-band migration failing on the name collision — see `deploy/k8s/README.md`'s "Upgrading to migration 0004" for the pattern (`0006` follows the same pattern; see the note below and its own README section). A migration whose DDL isn't representable in Drizzle's declarative schema (feature-detection, `CREATE EXTENSION`, partial/expression indexes with an operator class) is authored via `drizzle-kit generate --custom` — an empty, hand-written SQL file the normal declarative diffing never touches — rather than forced into `schema.postgres.ts`. The mobile companion's migrations are `0013_pairing_codes`, `0014_mobile_devices`, `0015_hitl_deliveries`, `0016_launch_idempotency_key` and `0017_ask_thread_owner_turn_start` in both dialects, after `0012_watcher_modes`; the offline outbox adds `0018_managed_delivery` and `0019_supervisor_outbox_state`. Unlike the `IF NOT EXISTS` index migrations above, `0018` and `0019` use plain `CREATE TABLE`/`ADD COLUMN` (the legacy SQLite init has its own `IF NOT EXISTS` forms); on Postgres `0018` takes a brief exclusive lock on `events` for the `ADD COLUMN` (see `deploy/k8s/README.md`). When a long-lived branch is merged, renumber its migrations after the ones already shipped and give them a journal `when` later than the newest shipped one: Drizzle's migrator skips any migration whose `when` is not newer than the last one applied, so a renumbered file with an older `when` would never run on an existing database. **Migration ledger (AGEN-67):** both SQLite paths reconcile `__drizzle_migrations` through `src/server/db/sqlite-migration-ledger.ts`, which replays the shipped SQL into memory, compares a live database by structure (columns, foreign keys, indexes by columns/DESC/collation/unique/`WHERE`, trigger SQL, never by name) and records the longest verified prefix inside one immediate transaction. Exceptions E1 to E3 (`sessions.metadata`'s `'{}'` default, nullable single-column non-INTEGER primary keys, the post-boot `ON DELETE CASCADE` on `SESSION_CHILD_FK_TARGETS`) are tested to still exist. A top-level data statement in a migration needs a `LEGACY_EQUIVALENTS` entry (today only `0012_watcher_modes`), a rebuilt table (`__new_x` renamed over `x`) is owned whole, and a new migration needs a legacy counterpart in `db/client.ts` or the ledger boot tests (U1, B8) fail. A later migration that does `DROP INDEX` by name must handle the legacy name too. Forced mode verifies the schema even when the ledger is at the tail (the legacy fast path is legacy-only; about 80 ms cold), a leftover `__new_*` table is a gap, a table's `CHECK`s, `STRICT`, generated columns and composite foreign keys are compared, and an entry whose object a later migration removes verifies only if that migration does. One process per SQLite file: two forced boots can race inside drizzle's `migrate()` (the loser fails and rolls back). Every existing-install boot that reaches `migrate()` reconciles first in forced mode, which throws a `MigrationLedgerError` (`index.ts` exits 1 with the message); the legacy path never fails boot over the ledger; `source-scan` U12 pins the one `migrate(` call site. The release that ships it (`LEDGER_SINCE_VERSION`) is a required stop before the legacy init is removed. Postgres is untouched.
- **Postgres search is `pg_trgm`-GIN-indexed (AGEN-27, migration `0006`)**: the migration adds one GIN trigram index per column/expression `PostgresSearchBackend`'s ILIKE queries already OR together (4 on `sessions`: `display_name`/`cwd`/`current_task`/`notes`; 6 on `events`: `content` and `raw_payload->>'prompt'|'message'|'summary'|'why'|'title'`), so Postgres serves each OR leg from its own index and combines them via `BitmapOr` — match semantics are unchanged (still the same OR-across-columns ILIKE). A single `COALESCE(...)`-then-index expression (mirroring SQLite's `EVENT_TEXT_COALESCE_SELECT`) was considered and rejected: `AiProposal`/`AiHitlRequest` rows (`src/server/services/ai/runner.ts`) can have both `content` (the proposal/prompt text) and `raw_payload.why` (the decision rationale) non-null on the same row, and `COALESCE` would silently prefer `why`, making `content` unsearchable for those two event types. The `events` indexes are partial (`WHERE event_type IN (...)`), restricted to `FTS_INDEXED_EVENT_TYPES` (`db/fts-ddl.ts`) — same searchable population as SQLite FTS5. `pg_trgm` needs `CREATE EXTENSION`, which some managed Postgres providers restrict to superuser; the migration wraps extension creation and index creation each in a `DO $$ ... EXCEPTION WHEN OTHERS ...` block, so an unavailable extension — or a build failure partway through (which rolls back every index attempted in that same BEGIN/EXCEPTION block, not just the one that failed — `IF NOT EXISTS` makes a retry idempotent) — degrades to a `WARNING` and the existing sequential-scan ILIKE path, never an aborted migration (drizzle-orm's postgres-js migrator runs every pending migration in one shared transaction) or a crash-loop. The migration runs `EXECUTE 'ANALYZE events'` before checking `pg_class.reltuples`: a never-analyzed table (a restored backup, a lagging autovacuum) reports `reltuples = -1` ("unknown"), not `0` — checking the 100,000-row threshold without analyzing first would silently skip the size guard; `reltuples` still `NULL` or negative after the ANALYZE fails safe to "skip and warn," never "assume small and build." `GET /api/v1/health`'s `searchIndexes: { present, missing[] }` field (`services/search/search-index-status.ts`, checked once at boot, querying `pg_index`/`pg_class` with `indisvalid` so an INVALID index — e.g. left behind by a failed `CONCURRENTLY` build — never counts as present) surfaces whether the 10 indexes are actually in place.
  **`SEARCHABLE_EVENT_TYPES_SQL_LIST`** in `postgres-search-backend.ts` renders the event-type restriction as literal SQL text via `sql.raw()`, never a bound parameter (percy AGEN-27 review) — a *bound* `event_type IN (...)` list is opaque to a generically-planned query, silently defeating the partial trigram indexes' `WHERE` predicate. It's built from a hardcoded, compile-time-known constant (never user input) and asserted `/^[A-Za-z]+$/`-safe at module load — the user's own query text remains a bound parameter throughout.
  **`searchSessions` runs unprepared** (`executeUnprepared()` — postgres-js `client.unsafe(text, params, { prepare: false })` on `db.$client` directly, bypassing the shared `executeRows()` helper other backends use) so it always sees the real bound ILIKE pattern; global client config (the `prepare` option `createDatabase()` leaves unset) is untouched, this is local to this one query. `sessions` is small enough that a single query, unprepared, is sufficient — unlike `searchEvents` below.
  **`searchEvents` runs an adaptive two-plan strategy** (percy AGEN-27 review, TB25/TB26 — `executeEventsQueryWithFallback()`), the end of a longer investigation: TB17 fenced the filter in a `WITH matched AS MATERIALIZED (...)` CTE before `ORDER BY`/`LIMIT`, which TB22 found regressed a common term (~50% selectivity) 0.18ms -> 1.8s at 1M rows by defeating early-`LIMIT` short-circuiting, so TB22 removed the fence in favor of a single unprepared query (the same shape `searchSessions` still uses). That fixed common terms, but investigation for TB25 (EXPLAIN ANALYZE against a worst-case fixture — identical `created_at` across 1M rows, so a genuinely *unique* match sits at the very end of `ORDER BY created_at DESC, id DESC` scan order, unlike percy's original 143-spread-out-matches fixture where early-LIMIT succeeded by luck) found the planner *never* picks the trigram BitmapOr plan for this query shape at any selectivity: Postgres's `ILIKE '%term%'` selectivity estimator can't know a literal substring is rare vs. common, so it always prefers walking `idx_events_created_at_id`. Fast (0.15-3ms) for every bucket except a genuinely rare/unique term, which degrades toward a near-full-table scan — measured 892-926ms at 1M rows, worse as `events` grows, the exact problem AGEN-27 exists to fix. Forcing the planner off that index on the same data proved the trigram plan is available for a rare/unique term (0.45ms) — a cost-misestimation, not a missing index. Plan B's own cost isn't constant, though: it scales with the size of the *matched* set — percy measured ~400ms at 500,000 clustered matches (TB27), so a term that's both common and clustered can push Plan B's total latency into the low hundreds of ms. It stays bounded (never degrades toward Plan A's near-full-table-scan failure mode) because `LIMIT` still applies on top of the Bitmap Heap Scan via a top-N heapsort — Postgres sorts only enough of the matched set to satisfy `LIMIT`, not the whole set.
  TB26's fix: **Plan A** runs the TB22 query (literal event types, `prepare: false`) inside a `db.$client.begin(...)` transaction with `SET LOCAL statement_timeout = '150ms'` (`PLAN_A_STATEMENT_TIMEOUT_MS`). If canceled (SQLSTATE `57014`, `isStatementTimeoutError()` in `sql-helpers.ts`), **Plan B** re-runs the identical query text/params in a *fresh* transaction with `SET LOCAL enable_indexscan = off` and `enable_indexonlyscan = off`, forcing the trigram path, with a generous timeout (`PLAN_B_STATEMENT_TIMEOUT_MS`, 10s — this plan is now believed correct, so a hang is a real problem, not an expected trade-off). Any other error propagates unchanged. Both `SET LOCAL`s are transaction-scoped — Postgres resets every `LOCAL` GUC at COMMIT/ROLLBACK regardless of connection pooling, so neither leaks onto a later pooled connection (verified by a dedicated test). Pagination is identical either way since both plans run the exact same `ORDER BY`/`LIMIT`/`OFFSET` — Postgres enforces the sort regardless of physical access path (a Bitmap Heap Scan gets an explicit `Sort` node before `LIMIT`). Whether Plan B fired is exposed via `SearchResult.debug.postgresEventsUsedFallback` (test/debug-only, not a routing contract) rather than by reading logs; `PostgresSearchBackend`'s constructor also accepts a test-only `{ forcePlanBForTesting: true }` option so pagination-parity tests can exercise Plan B through the real query-building code without a naturally-timing-out fixture. The test Postgres container needs `--shm-size=1gb` (not Docker's tiny default) — DSM allocation for parallel-plan queries under this suite's sustained load otherwise starves and surfaces as flaky multi-hundred-ms timings unrelated to the query plan (`.github/workflows/ci.yml`'s `test-postgres` job sets this). See `deploy/k8s/README.md`'s migration-0006 section for the operator-facing "run `ANALYZE events;` after a bulk import" note.

- **The vector scan (`services/ai/embeddings/vector-scan.ts`, `scanSessionSimilarity`)**: SQLite-only, exact cosine over the newest vectors of the active `(model, dim)`. Invariants: (1) it is the only production code that reads more than one row of `event_embeddings` (`embedding-service.ts` writes and does keyed reads); `embeddings-readers.guard.test.ts` fails if any other file under `src/` or `packages/` touches the table outside `src/server/db/`, and fails if any statement selecting `v.vector` lacks a `LIMIT` or the `INDEXED BY idx_event_embeddings_model_dim_event` clause (`scripts/` is not scanned, so the benchmark can seed and read). (2) `INDEXED BY` is deliberate: a missing index is an error (logged once as `ask_vector_scan_error`, `reason: "index_missing"`, and `getVectorScanIndexState()` reports `missing`), never a silent table scan. (3) Reading is keyset-chunked, newest first (`event_id < ?`, `ORDER BY event_id DESC`), in chunks of at most 256 KiB (`CHUNK_BYTES`; 16 rows at 4096 dims, never more than 256), and a `LEFT JOIN` plus `CASE WHEN e.session_id IS NOT NULL AND length(v.vector) = ?` (bound to `dim * 4`) means an orphan vector, or one whose stored size doesn't match the dimension, costs a row but no blob read (`length()` of a BLOB comes from the record header). (4) Between chunks it yields with `setImmediate`: a microtask yield starves I/O, and `setTimeout(0)` costs a timer-wheel turn per chunk. (5) There is ONE global pacer (module-level `debtMs` and a single shared sleep): each chunk's CPU time (`process.cpuUsage()` user plus system, through `ScanClock.cpuMs`, never more than the chunk's wall time; a clock with no `cpuMs`, as in tests, is charged wall time) is charged as debt of `busy * (1 - share) / share`, never wall time, because a read blocked on storage uses no CPU quota and sleeping on top of it buys nothing, and the debt is deliberately uncapped per chunk (a cap would let the scan exceed the share), one sleep pays it, and every other scan awaits that sleep, so all scans in the process together stay within `config.vectorScanCpuShare`; a scan loops `nextWait` and runs its chunk with no `await` in between so none issues a statement while another is asleep. (6) The budgets, `config.vectorScanMaxRows` and `config.vectorScanMaxMs` (stop reasons `row_budget` / `time_budget`, else `exhausted`), and the CPU share are read from `config` on every call (plain numbers, so a test can set them); `maxMs` runs from the scan's start, pacing included, and is checked after each chunk and again after a pacing wait (a scan always runs at least one chunk). (7) An orphan or a blob that isn't exactly `dim * 4` bytes is `skipped`, not scored (the SQL guard returns it as a null vector; the JS length check stays as a second line). The enricher (`vector-enricher.ts`) turns any scan error into "no semantic hits": enrichment is an optional extra and the turn goes on. - **The supervisor report gate is the only way to report about a session.** `src/supervisor/services/report-gate.ts` builds and sends every request that carries session data; a drift test holds those endpoint paths to that file, and a guard fails any other `fetch` under `src/supervisor` except the two sanctioned sends. Test-only seams (account-home overrides) are enforced by `check-no-test-seam-leaks.ts`/`check-no-exclude-provider-outside-tests.ts`.
- **Supervisor offline outbox (AGEN-83)**: when the server can't take a report, the gate keeps it in a bounded, private, per-session queue on disk (`services/report-outbox.ts`, under `~/.agentpulse/supervisor-outbox/`, created on the first append, so a healthy host does no filesystem work) and sends it later, in order. **Only managed-session state and events are queued.** Launch status and control status never are (they have no transition guards, so a late overwrite is worse than a lost update), nor is the closing report (`scan()` retries it), nor heartbeats or claims. The gate sends live and spills on `network`/`server`/back-pressure failures; once a session has queued entries, its later reports queue behind them; a root that isn't this account's own, private and plain disables the outbox and a failed send throws as it always did. Layout: one 0700 directory per session (`s-<sha256(sessionId)[0:32]>`) holding `session.json` and one 0600 file per entry, written atomically; a directory or head that can't be trusted is *held* (not read, not deleted; only an exclusion purge removes it), and one held session never blocks another. **Bounds** (`OUTBOX_LIMITS`): an entry of up to twice the server's 2 MiB body limit plus 4 KiB (about 4 MiB: a body is stored as a JSON string, which at worst doubles it), 500 events an entry, 8 MiB or 2,000 entries a session, 64 MiB in all, 256 sessions, 24 h of age. Past them, in order: the oldest non-head state entry is folded into the next state entry (`foldStateReports` mirrors the server's merge rules, `status` and `desiredThreadTitle` taking the later report's own value even when absent); then the oldest non-head events entries become one `ManagedEventsLost` gap entry; over the total, the same on the largest session; a new session past 256 is lost. A batch of more than 500 events, or too big for an entry, is split when queued, except that a body already sent once with a delivery id and at or under 2 MiB is never split (the server may have committed it, and pieces under new ids would not match its receipt); one over 2 MiB can't have been stored, so it is. **The oldest queued state report, which may be the one that creates the session on the server, is never folded; only the reports after it are.** Age-out never drops a state entry (aged ones fold into one retained head, aged events become a gap), so a never-delivered session still replays its creation first. A head that fails 8 times in a row over at least an hour is removed as lost; a failure with no answer at all is back-pressure and counts only once the head has waited out the 6 h budget below **and** the server has taken a send (a 2xx) since that head last failed that way, so a host whose heartbeat gets through while every replay times out doesn't poison its queue. Every loss is counted except an exclusion purge; the figure is an upper bound for attempted entries and can be a lower bound after a restart (losses since the last flush are held in memory; the gap entries still say how many events each stands for). Reconnect: a flush every 3 s, at most 50 sends a session and 100 a pass (about 33 requests a second), a random 0 to 5 s wait after the server returns, one send at a time per session, each with `X-AgentPulse-Replay: 1`; the session's chain is taken per send, so a live report waits behind at most one. A 500 on events for a session the server has no row for sends that session's oldest queued state report first. **Queued entries are re-judged against the exclude rules before every send** (`flushStep`): an entry for a session a rule now covers is not sent, its directory is purged (held entries included) and the session gets its one closing report; while the rules are invalid the whole flush holds (nothing sent, nothing purged); `scan()` does the same purge for sessions with queued entries and for sessions the gate no longer knows while rules exist.
- **Failure classes and the credential tripwire (AGEN-83)**: `classifyReportFailure` (`report-resilience.ts`) sorts a failed send: *network* (no answer, a timeout, or a 2xx that isn't JSON, so a captive portal's HTML page delivers nothing) keeps every entry: on a live send it latches the gate offline; on a replay the first no-answer in a pass backs that session off, uncounted, and moves on to the next session, and a second in the same pass ends the pass and latches the gate offline; *server* (408, 425, 429, 5xx) backs that session off 3 s doubling to 60 s, jittered 20% either way, `Retry-After` winning; *backoff* (`503 busy` with `Retry-After`) waits and never counts as a failure; *session* (`403 session_not_owned`) purges the session, counted lost; *entry* (`400` with `reserved_event_type`, `invalid_body` or `sessionId is required`, or `413`, too large for the server or something in front of it) drops that entry at once, counted lost; *credential* is only the server's three exact wordings (401 `Missing supervisor credential`/`Invalid supervisor credential`, 403 `Supervisor credential does not match target supervisor`); *stop* is everything else (404, other 4xx). A 401/403 that isn't one of those wordings comes from something in front of the server (a proxy, an auth edge) and is treated as back-pressure: it holds the whole flush, and counts toward the poison rule only once a head has waited more than 6 h on back-pressure (`BACKOFF_BUDGET_MS`). A credential rejection the tripwire hasn't confirmed (the first, or any over plain http to a non-local server) keeps the entry in the flush, isn't counted against it, and puts that session on a backoff so the next flush doesn't try it again 3 s later. One tripwire (`createCredentialTripwire`) serves the heartbeat, the gate, the bridge drain and in-session reporting: the first credential rejection only records its time, a second at least 10 s later confirms it, and any success (a send, a heartbeat, a drained report) forgets the first. A confirmed rejection runs `disposeRuntimesAndExit` (`fatal-exit.ts`): it disposes the managed Codex app-servers and headless Claude processes and exits 1 for the service manager, whatever the runtime count; interactive terminals aren't children and are left running. Over plain `http:` to a non-loopback address the tripwire never confirms (anything on the path could forge a rejection) and logs once, so a revoked host there keeps running. **Keep-alive**: a failed heartbeat of class network also latches offline, and while offline an extra heartbeat is tried every 10 s so the first answer lets the queue flow (any answer from the server, an error status included, clears the offline latch; only a 2xx also forgets a recorded credential rejection); registration retries network errors with its backoff instead of exiting. The watchdog (`shouldExitOnStaleHeartbeat`) exits only when the heartbeat is stale for `max(3 x interval, 90 s)` **and** the supervisor holds no managed Codex runtime, no headless Claude runtime and no live terminal bridge; not being able to count bridges within 2 s counts as "may be running". Otherwise it logs `server unreachable for Ns; keeping N managed sessions running; ...` once per outage. Queued reports deliberately don't keep it alive: they are on disk and the restarted supervisor replays them (a supervisor run by hand, or on Windows, replays only once it is started again). There is no offline ceiling.
- **Terminal-bridge spool (AGEN-83)**: the interactive bridge (`scripts/claude_terminal_bridge.py`) no longer holds a credential or opens a connection (its only socket is `AF_UNIX`; `claude-terminal-bridge.test.ts` holds the script to an allowlist of imports and calls). It writes each report (start state, each prompt typed, exit state, end event) as one 0600 file in `~/.agentpulse/interactive/<launchCorrelationId>/reports/`, stamped with `occurredAt` at the true moment and carrying the launch's `launchNonce` from `bridge.json` (which no longer has `server_url`, `supervisor_id`, `supervisor_token` or `api_key`; `scrubLegacyBridgeConfigs` removes them from a file an older supervisor wrote when the supervisor starts). The spool keeps at most 2,000 files and 8 MiB; past that a report is dropped and counted in `reports/lost`, which the drain turns into a lost-count event. It skips keystroke capture while the terminal is in line mode with echo off (getpass, sudo, ssh), but not in raw mode. `bridge-spool.ts` drains it inside the supervisor, every second, through `gate.reportState`/`reportEvents`, so the exclude rules apply to the bridge as to every other sender: the directory name is the id, the gate must have recorded it as an interactive launch (`isInteractiveLaunch`, persisted), the directory is judged by the cwd the gate learned at launch (the `cwd` in `bridge.json` is never read, since any process of the user can rewrite it), and a directory the gate doesn't know is excluded while rules exist. Each file is checked against a whitelist (exact keys, the two event types `InteractivePromptObserved`/`InteractiveSessionEnded`, size caps, the nonce); a file that fails is deleted and counted lost. At most 256 directories are followed, 50 files a directory and 200 a tick. A file is unlinked after `sent`, `queued` or `excluded`, and kept on `blocked` (invalid rules stop the tick) or a retryable failure; after three failed removals a report file isn't sent again: it is remembered by directory, name and file identity (inode, size, ctime and mtime), for at most 1,024 files; a supervisor restart forgets that and allows up to three more sends, which store again once the 72 h receipt has gone; a file rewritten from outside is a different file by that identity, except that at equal size within the same coarse timestamp it can look unchanged and is withheld until a restart (the bridge writes each report once, under a new name, and never rewrites one); a private spool file larger than the bridge ever writes (1 MiB) is removed and counted lost; the delivery id is written into the file by the bridge, so a crash between send and unlink resends the same id. The drain sends a file as a replay once it has waited more than `LATE_ARRIVAL_MS`, and every file present at its first pass after a start. **Because the gate now remembers an interactive launch on disk whatever the rules (the bridge outlives the supervisor and has to be found again), a host with no exclude rules writes `~/.agentpulse/supervisor-gate-state.json` once it launches an interactive session; if that file or its directory stops being private and plain, the gate treats it as invalid rules (nothing is reported or launched) until it is repaired or deleted, and the Hosts page shows the invalid flag.** Residuals: a spool dir the gate has no record of is dropped permanently while rules exist; a spool can hold content from a directory excluded while the supervisor was down (judged and unlinked unsent at the drain, but it was on disk at 0600); a drain's replay age is its in-memory first-seen time, so after a supervisor restart an old file reads as fresh and an outage-era prompt can wake the watcher once. **Residual:** A spool file is never dropped for its age: if the supervisor sent one and crashed before removing it, then stayed down for longer than the server keeps a delivery receipt (72 h), the file is sent again and its events are stored twice. Accepted: dropping a report after a long outage loses real work (a terminal state included), a duplicate costs a few repeated rows, and the rule everywhere in the outbox is that a possible duplicate beats a certain loss.
- **Offline outbox: what readers see, and its limits (AGEN-83)**: the Hosts page (`pages/host-outbox-view-state.ts`, `components/HostOutboxNotice.tsx`) shows one notice per host from the heartbeat's `outbox`: *catching up* (live lease, `pending > 0`, with the oldest time), *back online* (live lease, nothing pending, a flush within 24 h that delivered or lost something, amber when `lastFlushLost > 0`) and *offline* (lease expired, host advertises `offline_outbox`, hidden after 7 days); never for a revoked or pending host. While the tab is visible it refetches hosts quietly every 30 s (paused while the 15 s poll runs, which is on while any host is catching up) and once more when the tab returns to view; the card's `now` moves only when a fetch succeeded (`hooks/useHostsClock.ts`), so a healthy host never ages into "offline" on a stale page, and a failed refetch leaves the cards as they were and shows an inline "Couldn't refresh hosts. Showing what we last heard at ..." line. The session timeline shows an event's `occurredAt` when it has one (`lib/event-time.ts`), and the first row of a run of events stored more than 60 s after they happened says "arrived Nm late" (the title and screen-reader text give both times); rows stay in id order, so occurrence times can run backwards across a late run. A `ManagedEventsLost` row is amber and, like every system row, hidden in the Prompts and Conversation modes. Lateness in the UI (`createdAt - occurredAt`) is a different judgement from the server's `late` flag (the replay header). Limits: `occurredAt` is stamped on the supervisor's own clock, so a skewed host shows the "arrived late" suffix on every row, or beyond the server's window gets a null `occurred_at` and shows `createdAt`; a spool file drained more than 25 h after it was written gets a null `occurred_at` for the same reason. `pending` can drop with no matching delivery when an exclusion purge happens while a host is connected and backed off. **Known limit:** a live events batch whose body is over the server's 2 MiB limit gets a `413`, which is thrown to the caller of `reportEvents`, not queued and not counted lost. The per-event content clamp counts UTF-16 units, not bytes, so a single 1,000,000-character CJK event (about 3 MB as UTF-8) is lost this way too. A replayed state reopens a session the inactivity sweep had completed (intended). A late launch status is not queued; the awaiting-session deadline covers it. **Upgrade the server first, then the supervisors.** An older server ignores the delivery id, the replay header and `occurredAt`, so a new supervisor's replays dedupe only within the content window (the newest 50 rows) and carry no occurrence times. A rollback has two edges: a supervisor older than the spool never drains a new bridge's spool, and a supervisor rolled back to a version that predates the persisted `interactive` flag drops it on its next save of the gate state, so after upgrading again a surviving bridge's spool isn't followed. A bridge started before a supervisor update (a `bridge.json` with no `launchNonce`) warns once on stderr to restart the supervisor and launch a new session, and its reports are rejected as stale until it does; an old bridge that is still running keeps posting directly with the credential it read at start, until it closes. Client parity: web and MCP carry `occurredAt` and `outbox`; the iOS app's contract has to declare them (and show the notices) before it can use them, which is a follow-up, not part of this change. All of it is additive and optional, so an installed app keeps working.
- **Managed Codex approvals (AGEN-87)**: **the boundary, stated plainly**: the trusted host supplies both the text a person sees and the process that runs, so `presentationHash` is an ETag for what the server showed (it stops a stale view, a changed revision and a replay); it does not prove a person read anything, or that the display matches execution. Executed-equals-shown was measured for one command shape (Codex 0.163.0, macOS): a script run by it saw the same arguments the shown command names. **Nothing queues**: a request is reported live (`gate.reportApproval` bypasses the offline outbox and `queueBehind`; a queued request would reach the server after its runtime was gone and present a dead approval as answerable), and only the plain auto-answer `ManagedWarning` (a capped method name, never params) may queue. A request made during an outage appears late or not at all and is declined at its deadline. **Expiry is default-deny**: 20 minutes (`CODEX_APPROVAL_TTL_MS`, one site for server and supervisor), then `decline` (measured: nothing runs, the agent is told, work continues; `cancel` would throw the turn away for someone merely away). The tracker's own deadline is the TTL plus a minute from receipt, a request with under a minute left is declined rather than reported, and `ageMs` is the larger of monotonic and wall-clock age. **Nothing can be answered for an offline host** (`host_offline`; the card shows no answer buttons; the TTL declines); a decline recorded before the lease lapsed stays deliverable. **An accept has a 60 s delivery window** from `answered_at`; past it the host is handed a decline. An accept is re-judged inside the issuing transaction (`rejudgeStoredAnswer`: the person still exists, isn't disabled and still passes the owner rule, else the row closes `answer_withdrawn` and the host gets a decline). An accept issued with no host report closes `outcome_unknown` after 5 minutes and the card says it may have run. **What Stop guarantees (D16)**: no accept is issued after Stop commits; **an accept issued before Stop committed may still run**, and the bound is 3 seconds: the tracker delivers an accept only from a sync whose round trip was at most 3 s (otherwise it declines and reports `declined_slow_response`), and the next sync returns the row fenced. Stop fences inside `enqueueStopInTx` (after the control lock is taken, so a `control_busy` Stop fences nothing): `pending` rows and undelivered `answered` rows close `session_stopped`; delivered ones get `fenced_at` and are never re-issued. A Stop that times out unclaimed lifts the block, and only an answer given after the failed Stop can issue (that person saw the Stop fail). An accept answered before expiry may still issue inside the 60 s window past `expires_at`: they answered in time. **Issuing is the linearization point**: sync issues only through one guarded `UPDATE ... WHERE status = 'answered' AND fenced_at IS NULL AND NOT EXISTS (<stop queued or running>) ... RETURNING`, never select-then-return, and the answer's guarded update carries the same predicates; `tracker.fence(sessionId)` runs before the runtime lookup in `stopManagedCodexSession`. **What the person is shown (D7)**: the server builds, redacts, stores and hashes the presentation; **any change, in any field, makes the row not approvable** (`input === output` per field after sanitising and redaction). Not-approvable reasons are fixed codes (`redacted`, `invisible_chars`, `padded_text`, `lookalike_text`, `too_long`, `no_diff`, `no_command`, `no_cwd`, `write_stdin`, `network`, `grant_root`, `unknown_param`, `accept_not_offered`): a command over 4 KiB is `too_long` (**a command that is approvable is shown whole, wrapped, with no preview cut**; the 4 KiB `preview` on the list is a preview only); runs of more than 40 spaces or tabs, or more than 10 blank lines, are `padded_text`; `lookalike_text` covers any `\p{Zs}` other than U+0020, any `\p{Cf}`, U+2800, and a token (a path segment, for paths) mixing Latin with Cyrillic, Greek or fullwidth forms, in the command, `cwd`, `grantRoot` and paths (a wholly CJK path stays approvable, with a `nonAscii` flag). Decline is always possible. A revision bumps on every buffer change (the tracker mints it, the server updates text and hash only on a *pending* row and only for a higher revision, `expires_at` never moves), and an accept for an older one is `presentation_changed`; the host compares the answer's revision with its current one with no await before `respond` and declines on a difference. File diffs come from `item/started` `fileChange` items buffered **by `(threadId, itemId)`** (a notification that should carry a thread id and doesn't counts as no diff), plus `patchUpdated`; the tracker waits at most 2 s, and no diff is `no_diff`. Requests are not pinned to the session's own thread (subagent threads may ask legitimately; not measured). **A second request on an rpc id that is still open never replaces the first**: it is a conflict, one decline is written, the earlier request is made terminal and the new one is neither held nor reported; `deliverAccept` also requires that the held request is still the one in the table and rechecks (not disposed, not fenced, verdict `supported`, server enabled) at the write that runs a command; the server's `(session, epoch, rpc_id)` key answers `identity_conflict` for a repeat. **Hash and approval ids**: the hash is the ETag and the only thing an accept must carry; it is required for accept (`presentation_hash_required`), and the web sends the one it read. **Accept is human-only (D15)**: a signed-in person; MCP reads and declines (`list_pending_approvals`, `decline_approval`) and has no accept, because `agentpulse mcp install` puts a manage key in an agent's own config and a key that could accept would let an agent approve itself. Under `DISABLE_AUTH` every caller counts as human, the flag's existing posture. **No AI path can answer**: a guard test pins `answerApproval(` callers to the one route file. **Operational state (D9)**: an open approval holds a `metadata.permissionWait` id `approval:<approvalId>`, so the existing machinery gives WAITING (it outranks `isWorking`) and the `permission_wait` push on the 0-to-1 transition; `processHookEvent` drops a hook whose `tool_use_id` starts `approval:` (counted, still 200), the boundary branch keeps `approval:` ids and clears the rest, `foldOldestIdsIntoAnon` never folds them, so a forged `Stop`/`UserPromptSubmit`/`PostToolUse` can't hide a live request; the sweep (`sweepApprovals`) repairs a wait id with no open row and an open row with no id (no push, `prevStatus` and `semanticStatus` untouched); `classifySession` returns `blocked`/`hitl_pending_long` early for such a session, so it is never `stuck` or `risky`. Timeline events carry **fixed text only** ("Codex asks to run a command", "Codex asks to change N files", and `ManagedApprovalResolved` with one fixed word), never command text, because team mode shares session reads while the approvals read is owner-or-admin; the watcher and Ask see the fixed `PERMISSION:` line, which a hook writer can forge, so nothing treats it as authority; approval text is not indexed for search or embeddings. **The exclude rule (D10)**: the tracker declines locally and reports nothing, not even a warning, when the session is excluded or blocked, or when `cwd`, any `path`/`movePath` resolved against it, or `grantRoot` is excluded (invalid rules count as excluded); a session excluded while requests are pending is declined locally and the gate's contentless closing report closes its rows `session_stopped`; **the server never learns about exclusion**. A command string isn't parsed, so text naming an excluded path inside `command` is still reported when `cwd` isn't excluded. **The protocol gate (D18)**: per Codex binary (path, version, size, mtime), `codex-protocol.ts` hashes the approval-relevant part of `codex app-server generate-json-schema --experimental` and gives `supported` only when the hash is in `SUPPORTED_CODEX_SHAPES`, the version is at or above the floor (0.163), isn't in `BLOCKED_CODEX_VERSIONS`, and **the transport rule** passes: the server URL must be https or loopback (`credentialRejectionMayConfirm`), else `insecure_transport`. Anything else is `unsupported` (reason: `version_unknown`, `below_floor`, `blocked_version`, `generator_failed`, `shape_unknown`, `useragent_unparseable`) and the runtime declines every approval locally with one `ManagedWarning` carrying a fixed reason. The verdict rides in the session's `providerCapabilitySnapshot` as `agentpulseApprovals`; absent means an older supervisor. A shape hash can't see a new version reusing a known field with changed meaning; the compensations are the `--real` canary on each Codex release, the one-line blocked list, the floor, and the per-request allowlist (`COMMAND_APPROVAL_PARAMS`/`FILE_CHANGE_APPROVAL_PARAMS`: a non-null key not in the schema makes the request decline-only `unknown_param`). `RpcClient` now answers server requests: an unknown method gets `-32601`, and every server request is default-denied unless a handler claims it. **Managed Codex runs over stdio (D20)**: `codex app-server` is spawned with JSONL on stdin and stdout and **no listening socket**, so no second local client can answer an approval (the previous `--listen ws://` listener let any local process do so; versions before this one leave it open on managed Codex sessions, so upgrade supervisors and kill any `codex app-server --listen` left behind). `managedCodexUrl` and the runtime `url` are gone from new sessions' metadata and from `ManagedSessionStart` (no reader existed in the server, web or MCP). ## Feature parity across clients

Every new feature, and every change to an existing one, must address parity across all AgentPulse clients. Do this in the plan, before implementation. A feature isn't done when only the server and the web dashboard have it.

| Client | Where | What parity means |
|---|---|---|
| Web dashboard | `src/web/` | Every user-visible capability is reachable from the UI. |
| MCP server | `packages/agentpulse-mcp/` | Read and act through tools where the scope model allows. The wire types are vendored, so keep the copy and its parity tests in step. |
| iOS companion app | Separate, closed-source repository (not in this repo) | It consumes the REST/WebSocket/push contract. A feature a phone user would use or need to see gets an iOS implementation, either in the same campaign or as a linked follow-up ticket. |
| Telegram / Ask | `src/server/services/channels/`, `services/ask/` | Only where the feature is something a person would ask for or be notified about. |

Rules:

- **Every plan has a `Client parity` section.** For each client above, it gives one of three verdicts:
  - **implemented in this campaign**, with the phase named;
  - **follow-up**, with the ticket ID;
  - **not applicable**, with a one-line reason.

  An empty section, or silence about a client, doesn't count.
- **Contract changes are parity changes even when nothing new is visible.** That covers a DTO field added, renamed or removed, a new or changed WebSocket broadcast, a new refusal code, push payloads, pagination, and scope classification. The iOS app decodes these. Name the iOS impact, and keep additive changes backward compatible for an app version that's already installed.
- **Server-internal features still get the check.** Examples: supervisor, relay, retention. If the feature changes what a user can observe (a new state, a count, a host condition), every client that shows that thing needs it.
- **Follow-up tickets go in the AGEN Plane project** (see Plane Project below) and are linked from the feature's ticket.

## Deployment

- **Local (SQLite default):** `docker run -d -p 127.0.0.1:3000:3000 -v agentpulse-data:/app/data -e DISABLE_AUTH=true` (use `127.0.0.1:` prefix to avoid publishing auth-disabled server on all host interfaces)
- **K8s base (SQLite):** `kubectl apply -k deploy/k8s/` (uses Authentik SSO + Traefik IngressRoute; image pinned by SHA; see `deploy/k8s/README.md`)
- **K8s Postgres overlay:** `kubectl apply -k deploy/overlays/postgres/` — see `deploy/overlays/postgres/README.md` for pre-flight steps (context check, DB + user creation, `secret-patch.yaml` fill-in). Rolling deploys are safe: boot serialization uses a session-level `pg_advisory_lock` on the migration client connection.
- **Relay:** `curl -fsSL --proto '=https' https://your-server.example.com/setup-relay.sh | bash` (asks for the key on the terminal; `AGENTPULSE_KEY` or `--key` for unattended installs). The served installers are embedded in the server at build time (`src/server/installers.ts`, Bun text imports), and `/health`'s `clients` checksums hash the same strings; `bun run check:bundled-installers` proves the bundled build serves them. Tests import `scripts/relay.ts` as a module only via `"./relay.ts?module"` (Bun caches by path; `check:installers` enforces it).
- **Installers:** `scripts/install-local.sh` and `scripts/setup-relay.sh` share the `agentpulse-bun` and `agentpulse-pkg-hint` blocks, held byte-equal by `scripts/installer-shared-blocks.test.ts`, so a Bun bump happens in one place.
- **Docker image:** `ghcr.io/jstuart0/agentpulse:<sha>` (linux/amd64; tagged by commit SHA — see `scripts/build-and-push.sh`)
- **Telemetry:** Cloudflare Worker + D1 (default homelab endpoint; configurable via `TELEMETRY_ENDPOINT`)

## OSS Hygiene

When preparing changes for commit or push to the public repository:

- sanitize environment-specific values first
- never commit real domains, internal IPs, API keys, hostnames, personal paths, cluster details, or private infrastructure identifiers unless they are intentionally public
- if a local working change requires private values to function, replace them with safe placeholders before commit
- after push, you may restore local/private values in the working tree if needed, but do not leave them committed
- treat deployment manifests, setup scripts, config files, screenshots, and docs as high-risk for accidental private leakage

Public git history is the source of truth. Local convenience must not leak into commits.
