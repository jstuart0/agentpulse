Observability vs. orchestration for AI coding agents

Tools for coding agents tend to do one of two jobs. Observability tells you what your agents did. Orchestration starts them, steers them and decides where they run. Knowing which you need saves you from installing more than you'll use.

Observability: knowing what happened

Observability tools read what an agent emits, through hooks, transcripts or logs, and turn it into something you can look at. Typical questions they answer:

  • Which sessions are running, and which need me?
  • What did I ask this agent, and what did it change?
  • How many tokens or how much money did this cost?
  • Where did that session go wrong?

The cost of adoption is low. You install hooks, and the agents behave exactly as before. You can't act on what you see, though. To answer an agent, you still go back to its terminal.

Orchestration: deciding what happens next

Orchestration tools own the agent's process. Because they started it, they can send it a prompt, stop it, restart it or start more like it. Typical jobs:

  • Launch a session from a template, with the right directory, model and instructions.
  • Send a follow-up prompt without being at the machine.
  • Route work to the machine that has the repository or the hardware.
  • Approve or decline what an automated watcher proposes.

The cost is higher. Something has to run on each machine to hold the processes, and it needs credentials strong enough to launch programs.

Side by side

ObservabilityOrchestration
Data sourceHooks, transcripts, logsA process the tool started
Works on sessions you started in a terminalYesNo, only on sessions it launched
Can act on a sessionNoYes: prompt, stop, retry
Installs on each machineHooks (and a relay for a remote server)Hooks plus a long-running supervisor
Credential riskRead and write eventsCan run programs on your machines

Choosing

Start with observability if you mostly sit at one machine and your problem is keeping track of several tabs. It's low-risk and quick to undo.

Add orchestration when you start tasks and walk away, run agents on more than one machine, or want to launch work from your phone or another agent.

How AgentPulse handles both

AgentPulse does both, and you choose how far to go. Installed with --skip-supervisor, it's observability only: hooks and a dashboard, nothing that can launch a program. With the default install, a local supervisor adds launch and control on the same machine. With a remote server, relays and a supervisor per host, you get one dashboard that watches every session and controls the ones it launched.

Sessions you started yourself in a terminal stay observe-only either way. API keys are scoped the same way: observe keys can read but never act, and only manage keys can launch.
